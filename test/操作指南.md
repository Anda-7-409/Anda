# 实验一：能力权重路由评测 — 保姆级操作指南

> 本指南假设你**从没跑过评测脚本**，从"打开终端"开始一步步带你走完全程。
> 对应《实验一_能力权重路由评测方案.docx》第 6 节 S1~S6。
> 全程只需项目已有的 `.venv` 环境，不装任何新依赖。

---

## 0. 这个实验在干什么（30 秒版）

你的项目里每个模型有一组"能力权重"（`AI/models.json`），它决定路由时谁排第一、
失败了先降级到谁。答辩时如果被问"chat=9、tool_use=8 这些数字怎么来的"，
现在可以用这套脚本给出数据答案：

1. 拿 90 条固定用例（4 种能力），**绕过降级链**，逐个直连模型提问；
2. 自动判分（答得对不对）+ 记录性能（首字多快、总共多慢、成不成功）；
3. 汇总成 3 张表，和现行权重对照 → 有依据地保留或调整权重。

最终产物：`test/results/raw.csv`（原始数据）+ `test/results/summary.md`（三张汇总表，
可直接贴进论文/PPT）。

## 1. 认识 test 目录

```
test/
├── 操作指南.md          ← 本文件
├── run_eval.py          ← 主评测脚本（真正发请求、记数据的就靠它）
├── judge.py             ← 判分器（被 run_eval.py 调用，一般不单独跑）
├── summarize.py         ← 汇总（评测跑完后跑一次，出三张表）
├── validate_cases.py    ← 用例集校验（正式评测前必须先跑）
├── cases/               ← 90 条评测用例（JSON，可自己增删改）
│   ├── chat.json        20 条：通用问答，按"关键点"判分
│   ├── tool_use.json    30 条：覆盖项目全部 14 个工具 + 2 条边界用例
│   ├── code.json        20 条：写代码任务，程序里预置了测试断言
│   └── reasoning.json   20 条：数学/逻辑题，答案唯一可自动判
└── results/             ← 所有产出都在这（第一次跑之前是空的）
```

**你平时只需要记住 3 条命令**：`validate_cases.py`（校验）、`run_eval.py`（评测）、
`summarize.py`（汇总）。其余都是被调用的。

## 2. 开始前的一次性准备（每台电脑做一次）

### 2.1 打开终端并进入项目根目录

在 VS Code / Trae 里打开项目后，按 `` Ctrl+` `` 打开内置终端。
确认提示符末尾路径是 `Anda`（项目根目录）。后面所有命令都默认在这里执行。

### 2.2 激活虚拟环境

```powershell
.venv\Scripts\activate
```

✅ 成功标志：提示符前面出现 `(.venv)` 字样。
❌ 如果报 `无法加载文件...因为在此系统上禁止运行脚本`，执行一次：

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

然后重新激活。

### 2.3 检查 API Key（`.env` 文件）

用记事本/IDE 打开项目根目录的 `.env`，确认有这两行且等号后面不是空的：

```
GLM_API_KEY=xxxxxxxx          ← 智谱平台（glm-4.7-flash 等）
SILICONFLOW_API_KEY=xxxxxxxx  ← SiliconFlow 平台（星辰/Xing4.0、DeepSeek、Qwen 等）
```

- 智谱 Key 在 https://open.bigmodel.cn 申请；
- SiliconFlow Key 在 https://siliconflow.cn 申请；
- **免费的 glm-4-flash、glm-4.7-flash、glm-4-flash-250414、Qwen3.5-4B 等够跑大半实验**。

✅ 确认方法：评测时脚本会自动读取；没读到会打印 `[跳过] xxx：环境变量 ... 未配置`，
看到这句就是对应 Key 没配。

### 2.4（可选）本地模型 Ollama

`mimo9b:latest` 走本机 Ollama，不花钱但要先启动：

```powershell
ollama serve          # 保持这个窗口别关
ollama pull mimo9b    # 第一次用先拉模型（约 5GB，只需一次）
```

✅ 确认方法：浏览器打开 http://localhost:11434 看到 `Ollama is running`。

### 2.5 看一眼现有模型与权重（帮助你规划评测顺序）

```powershell
python -c "import json;m=json.load(open(r'AI\models.json',encoding='utf-8'))['models'];[print(f\"{x['model_id']:<45}{x['provider']:<12}{x['ability_weights']}\") for x in m]"
```

会打印每个模型的 `model_id / 厂商 / 各能力权重`。
**`model_id` 是评测命令的 `--model` 参数，必须原样复制**（含大小写、斜杠）。

## 3. 第一步：校验用例集（S1，必做，1 秒）

```powershell
python test\validate_cases.py
```

✅ 期望输出：

```
工具注册表解析：14 个 -> ['calendar_export', 'code_gen', 'doc_parse', ...]
  chat.json: 20 条 PASS
  tool_use.json: 30 条 PASS
  code.json: 20 条 PASS
  reasoning.json: 20 条 PASS

全部通过，共 90 条用例。
```

**这条检查了什么**：JSON 语法、用例 id 不重复、每个工具名真实存在于
`agent_service.py` 的注册表、code 用例的断言能对上题面、每个 chat 用例都有判分
关键点。**没 PASS 之前不要往下跑**——它保证判分器不会把所有模型误判。

## 4. 第二步：空跑 dry-run（不花钱，强烈建议）

```powershell
python test\run_eval.py --ability all --model all --dry-run
```

输出长这样（数字以你当前 models.json 为准）：

```
评测计划：ability=all model=all rounds=3 limit=全部 out=...\results\raw.csv
  chat: 20 用例 × 10 模型 × 3 轮
  tool_use: 30 用例 × 5 模型 × 3 轮
  ...
[dry-run] 共约 1860 次请求，未发送。
```

**怎么读**：`用例数 × 模型数 × 轮次` 就是这个能力的总请求数。
只统计"有权重"的模型（权重 0 或 `—` 的不测，反正路由不会派给它）。
最后一行是预估请求总数，用来估成本。**确认数字符合预期再正式跑**。

## 5. 第三步：冒烟测试（S3，每模型×能力 2 元钱的保险）

### 5.1 什么是冒烟、为什么必须先做

冒烟 = 每个模型×能力只跑 2~3 条用例，目的是**提前发现判分规则设计得合不合理**、
网络通不通、Key 对不对。冒烟数据写到单独的 `smoke.csv`，不混进正式数据。

### 5.2 冒烟命令模板

```powershell
python test\run_eval.py --ability chat --model glm-4-flash --limit 2 --rounds 1 --out test\results\smoke.csv
python test\run_eval.py --ability tool_use --model glm-4.7-flash --limit 2 --rounds 1 --out test\results\smoke.csv
python test\run_eval.py --ability code --model Qwen\Qwen3-8B --limit 2 --rounds 1 --out test\results\smoke.csv
python test\run_eval.py --ability reasoning --model glm-4.7-flash --limit 2 --rounds 1 --out test\results\smoke.csv
```

> 注意 `--model Qwen\Qwen3-8B`：model_id 里的 `/` 在 PowerShell 也能正常传入，
> 建议从 2.5 节的输出里**整体复制**。

### 5.3 冒烟输出逐行解读

```
  [glm-4-flash|chat] chat_001 r1 ok=True PASS score=1.00 命中 2/2
     └ ok=True      请求成功（拿到回答）
     └ PASS         判分通过
     └ score=1.00   关键点全命中
  [glm-4.7-flash|tool_use] tool_001 r1 ok=True PASS score=1.00 正确调用 ['schedule_query']
     └ 模型正确发起了 FC 工具调用
  [glm-4.7-flash|tool_use] tool_017 r1 ok=False FAIL score=0.00 (重试1次) http_429: ...
     └ 429=限流，不重试第二次、不判分，只记录 ← 这本身就是稳定性数据
```

### 5.4 冒烟要人工检查的 3 件事

1. **PASS/FAIL 是否符合你的直觉**：如果你看着回答明显正确却 FAIL，
   通常是判分太严 → 去改 `cases/chat.json` 里对应用例的 `kp`（给关键点多加同义写法，
   例如 `"100"` 加上 `"100℃"`、`"一百"`）；
2. **tool_use 的 FAIL 详情**：`期望 [...] 实际调用 [...]` 说明模型选错了工具（真实数据，
   保留）；`task 缺关键参数` 说明模型选对工具但 task 描述漏了重点（可适当放宽
   `params_must`）；
3. **code 全 FAIL**：检查断言与题面函数名是否一致（`test\validate_cases.py` 会查，
   但模型可能写了别的函数名——那是模型的问题，不是用例的问题，保留）。

> ⚠️ **修改判分规则（kp / params_must / tests）后，已测过的数据必须作废重测**，
> 否则新旧口径混在一起，数据就不可信了。

## 6. 第四步：正式评测（S4，可分几天跑）

### 6.1 评测顺序建议（控制变量 + 控成本）

原则：**同一模型×同一能力在同一天同一时段集中测完**（避免网络波动污染对比）。
建议按"能力"为单位推进，每个能力下从免费模型开始：

| 天 | 内容 | 命令示例 |
|---|---|---|
| 第 1 天 | tool_use（核心创新，权重最高的能力） | `--ability tool_use --model all --rounds 3` |
| 第 2 天 | reasoning + code | `--ability reasoning --model all --rounds 3` 等 |
| 第 3 天 | chat + Ollama 本地模型 | `--ability chat --model all --rounds 3` |
| 机动 | 429 被打爆的模型补测 | 单独指定 `--model` 补跑 |

### 6.2 正式命令（就两种用法，别的都不用记）

```powershell
# 用法 A：一个模型 × 一个能力
python test\run_eval.py --ability tool_use --model XingChenAGI/Xing4.0-29B --rounds 3

# 用法 B：某能力下全部有权重的模型依次跑完
python test\run_eval.py --ability reasoning --model all --rounds 3
```

所有参数一览：

| 参数 | 必填 | 说明 | 默认 |
|---|---|---|---|
| `--ability` | 是 | `chat` / `tool_use` / `code` / `reasoning` / `all` | — |
| `--model` | 是 | models.json 的 `model_id`，或 `all` | — |
| `--rounds` | 否 | 每条用例重复次数（实验文档冻结为 3） | 3 |
| `--limit` | 否 | 只取前 N 条（冒烟专用，正式跑不要带） | 0 |
| `--out` | 否 | 输出 CSV 路径 | `test\results\raw.csv` |
| `--dry-run` | 否 | 只打印计划不发请求 | — |

### 6.3 运行中你需要知道的行为

- **数据追加写入** `test\results\raw.csv`：中途 Ctrl+C 或断网，**重新执行同一命令即可续跑**，
  已完成的行不会丢（判分以行计，汇总按行平均）；
- **没配 Key 的模型自动跳过**，打印 `[跳过] ... 环境变量 ... 未配置`；
- **无该能力权重的模型自动跳过**，打印 `[跳过] xxx 无 tool_use 能力权重`——这是正常的；
- **超时/网络错误自动重试 1 次**（输出里带 `(重试1次)` 前缀）；重试仍败记
  `error_type=timeout/network`；
- **429 永不重试**：记 `error_type=http_429` 后继续下一条。429 出现频率高的模型，
  恰好是你当初调低它权重的理由，这些行不要删。

### 6.4 raw.csv 每一列是什么（12 列）

| 列名 | 含义 | 举例 |
|---|---|---|
| `case_id` | 用例编号 | `tool_017` |
| `ability` | 能力 | `tool_use` |
| `model_id` | 被测模型 | `glm-4.7-flash` |
| `round` | 第几轮（1~3） | `2` |
| `provider` | `厂商:model_id` 组合串 | `zhipu:glm-4.7-flash` |
| `ok` | 请求是否成功（拿到回答或工具调用） | `True` / `False` |
| `score` | 判分得分 0~1（ok=False 时为 0，不参与准确率统计） | `1.0` |
| `judge_result` | 判分是否通过 | `True` / `False` |
| `error_type` | `none` / `http_429` / `http_401` / `timeout` / `network` / `stream_error` / `empty` | `none` |
| `ttft_s` | 首块延迟（秒），非流式回退时为空 | `1.063` |
| `latency_s` | 端到端耗时（秒） | `1.766` |
| `resp_preview` | 回答/工具调用前 200 字，人工抽查用 | `...` |

**不要手工修改 raw.csv**。确有异常样本要剔除时，保留原始文件，在论文里写明剔除规则。

## 7. 第五步：汇总出表（S5，评测完跑一次）

```powershell
python test\summarize.py
```

- 默认读 `test\results\raw.csv`，生成 `test\results\summary.md` 并打印到屏幕；
- 若要汇总冒烟/回归数据：`python test\summarize.py --csv test\results\smoke.csv`
  （会生成 `summary_smoke.md`，不覆盖正式汇总）。

### 三张表怎么读、怎么用

**表 A（质量表）**：模型×能力的准确率，单位 %。
- 口径：**只统计请求成功（ok=True）的轮次**。一个模型准确率高但成功率只有 60%，
  不能说它质量好——质量层看 A 表，可用性看 B 表，分开陈述；
- 论文写法："`Acc_tool=93.3%`（n=30×3 轮中成功 27 轮）"。

**表 B（性能表）**：
- `TTFT P50/P95`：首字延迟中位数与 95 分位（用户"等第一个字"的体感）；
- `耗时 P95`：整段回答完成时间的 95 分位；
- `成功率`：ok=True 的行占比，**含 429**——429 多会拉低成功率，这正是真实线上情况；
- 论文写法：结合 B 表解释 timeout 取值（如 P95≈45s 的模型 timeout 设 90s）。

**表 C（H1 检验表）**：把"现行权重从高到低排序"与"实验准确率从高到低排序"对照。
- `秩差` = 同一模型在两个排序里位次差的平均；
- **秩差 ≤ 1.0 → 结论"基本一致"**：现行权重有数据支撑，答辩时直接引用；
- 秩差 > 1 → 结论"需调整"，按第 8 节调参，并把该表截图/誊抄进实验文档第 7 节表 C。

---

## 8. 第六步：调参与回归（S6）

1. **决定改什么**：只对表 C 标"需调整"的能力动手。结合表 A（质量）+ 表 B（延迟）：
   - 质量明显更高的模型 → 权重上调；
   - 质量同档但 TTFT P95 明显更低 → 同档内微调顺序（对应实验文档 8.1 规则）；
   - 超时频繁的模型 → 按 `P95 耗时 × 1.5~2` 修 `timeout`；
2. **改 `AI/models.json`**：只改 `ability_weights` 和 `timeout` 两个字段，改完先别提交；
3. **登记调参记录**（实验文档第 7 节表 D）：一行一条 ——
   `日期 | 能力 | 模型 | 旧权重→新权重 | 引用的数据（表A/B哪一行）| 回归结论`；
4. **回归验证**：用 30% 用例（如 tool_use 取前 9 条）复测被改模型，确认没有变差：

   ```powershell
   python test\run_eval.py --ability tool_use --model <被改模型> --limit 9 --rounds 1 --out test\results\regress.csv
   python test\summarize.py --csv test\results\regress.csv
   ```

5. 回归通过后，再提交 models.json 的修改（配合 git，能回答"权重什么时候、为什么改"）。

## 9. 数据可信度规则（答辩被质疑时的护身符）

1. **判分规则先于实验冻结**：`judge.py` 的规则改一次 = 已测数据作废重测。确需修改，
   在实验文档记录"何时改了什么、哪些数据重测了"；
2. **每条用例 3 轮**：模型有随机性，单次结果不作数；汇总自动取均值；
3. **剔除规则提前定**：只允许剔除"重试后仍失败的整行"（它们本来就不参与准确率），
   不允许剔除 FAIL 的行——FAIL 是宝贵数据；
4. **可复现**：评测脚本 + 用例集 + raw.csv 全部提交 git。答辩时说
   "老师可以现场抽一条用例复跑"，这是最强的可信度证明；
5. **标注时效**：论文注明实验日期与 model_id（含版本号），因为云厂商模型会静默升级。

## 10. 故障排查（按报错原文查）

| 你看到的 | 原因 | 处理 |
|---|---|---|
| `无法加载文件 ... 禁止运行脚本` | PowerShell 执行策略 | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 后重新激活 venv |
| `[跳过] xxx：环境变量 GLM_API_KEY 未配置` | `.env` 缺 Key 或没保存 | 补 Key 后重跑（脚本每次启动都重新读 .env） |
| `工具注册表解析到 0/14 个` | `agent_service.py` 注册代码格式变了 | 检查 `orchestrator.TOOLS["xxx"] = { "desc": ...` 的书写格式是否还匹配 |
| `http_401` | Key 错误/过期 | 到对应平台重新生成 Key |
| `http_429` | 模型限流（免费额度用尽或高峰期） | 不用处理，换个时段继续；这行数据保留 |
| `timeout`（重试后仍超时） | 模型太慢或 Ollama 没启动 | Ollama：确认 `ollama serve` 在跑；云端：偶发属正常，连续超时再查网络 |
| `empty` | 模型返回空内容 | 偶发重跑即可；某模型频繁出现则记入分析（真实不稳定数据） |
| `网络错误 proxy` 类 | 系统代理拦截 | 关闭代理软件，或设置 `NO_PROXY=localhost,*` 后重跑 |
| `PASS/FAIL 与直觉不符` | 判分口径问题 | 冒烟阶段发现：改 `cases/*.json` 的 `kp` / `params_must`，然后**重测该用例全部数据** |
| `code` 判分总报 `断言失败/异常` | 看输出里冒号后的异常信息 | 若是 `NameError`（函数名不对）是模型问题，保留；若是用例断言本身写错，修 tests 并重测 |
| Excel 打开 raw.csv 中文乱码 | 编码 | 文件是 utf-8-sig，Excel 应正常；其他工具请指定该编码 |
| 控制台中文乱码 | 旧版控制台 | 先执行 `chcp 65001` 再跑命令 |

## 11. 成本与工作量预估

| 项 | 数值 |
|---|---|
| 总用例数 | 90 |
| 全量请求（4 能力 × 全模型 × 3 轮） | 约 1900~2600 次（取决于有权重模型数） |
| 免费模型占比 | 智谱 flash 系列 + SiliconFlow 免费档，约占请求量 6~7 成 |
| 付费模型预估花费 | 8B 级模型 3 轮全量，通常 < 5 元 |
| 总时长 | 分 3~4 个半天；单条请求 2~120s 不等，脚本自动推进无需盯屏 |

## 12. 一页速查（复制即用）

```powershell
# ① 激活环境（每次开新终端都要）
.venv\Scripts\activate

# ② 校验用例集（改过 cases 后重跑）
python test\validate_cases.py

# ③ 空跑看计划
python test\run_eval.py --ability all --model all --dry-run

# ④ 冒烟（换模型名逐个来）
python test\run_eval.py --ability tool_use --model glm-4.7-flash --limit 2 --rounds 1 --out test\results\smoke.csv

# ⑤ 正式评测（按能力推进）
```
