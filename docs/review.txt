## auth.py 总评
分层思想你已经懂了（Q1/Q3 全对），目前的两个薄弱点很清晰：

1. “接口的访问者是谁”意识 （Q2/Q4）——每写一个接口前先问：这个请求是 JS 发的还是浏览器直接发的？答案决定了返回 JSON 还是重定向、能不能抛 401；
2. 业务逻辑归位的直觉 （Q7）——记住口诀“自动做什么 = service；怎么进怎么出 = 路由”。
建议把这 8 题的错题结论浓缩进你 auth.py 的文件头注释里，比如加两行：
# 接口只表态（200/400/401/422），不做页面导航；导航由前端决定。
# 业务逻辑（含校验后的副作用）一律写进 auth_service，路由层保持纯转发。`

(b) 如果这个接口改用`GET /logout` ，让用户 在浏览器地址栏直接输入`/auth/logout` 就能退出，
会有什么安全隐患？（提示：想想除了你，还有“谁”会替用户发 GET 请求——浏览器访问网页时会不会顺手带上什么？
可以联想`<img src="...">` 能不能偷偷触发这个请求。）

核心答案一个词： CSRF（跨站请求伪造） 。
GET 的致命弱点是： 浏览器加载任何资源都可能顺手发 GET，且不需要用户知情 。恶意网页里写一行：
HTML
`<img src="https://你 的域名/auth/logout">`
受害者只要打开那个恶意页面，浏览器就去加载这个“图片”，实际发出了一个登出请求—— 
用户的登出操作被第三方代劳了 。同理，邮件客户端的链接预览、浏览器的预加载也都会提前 GET 一遍。
但要给你补一个本项目的真实细节 （评委追问时的加分点）：
CSRF 之所以经典成立，是因为很多系统用 Cookie 传凭证——浏览器发请求时 
自动带上 Cookie。而你们的 token 放在 localStorage、
由 JS 手动塞进`Authorization` 头——`<img>` 标签 带不上这个头 ，
所以这个项目里经典的 img-CSRF 其实打不进来。
这属于“localStorage + Bearer 头”方案的天然优势（代价是少了 Cookie 的便利性）。
尽管如此，“GET 产生副作用”仍是 HTTP 规范明确禁止的反模式（GET 应当是安全幂等的）规范层面就该把登出设计成 POST。
