下面是 仍然值得打磨的 6 处细节 ，按优先级排：

### 1. Backend/models/ 注释写错了（高）
你写的注释是：

1

`-models- (ORM 模型) //用于识别用户上传的课表图片，提取课程信息、时间、地点等`

"识别课表图片"是 AI / OCR 层的职责 ，不是 ORM 模型的职责。`models/` 里应该放的是 SQLAlchemy / Peewee 的表结构定义（User、Schedule、Reminder、Review、Consult、Task、Knowledge 等）。建议改成：

1

`-models- (ORM 模型) //用于定义数据库表结构，包括用户、课表、提醒、复习计划、咨询记录、任务、知识库等`

图片解析/OCR 建议单独放到`skill/ocr_schedule.py` 或`AI/` 下的`ocr.py` ，否则读者会误以为 ORM 在做视觉识别。

### 2. Skill 层命名未统一（中）
你保留了`agent_search.py` /`agent_system.py` /`agent_gpa.py` /`agent_review.py` ，但新加了`base.py` 。既然已经决定用`skill_` 前缀（`base.py` 的存在暗示了这一点），建议一并改掉，否则两套命名并存：

`skill/
├── base.py
├── skill_search.py
├── skill_system.py
├── skill_gpa.py
└── skill_review.py`

同理，`Backend/usr/` 目录名也偏"旧风格"——既然里面是`auth.py` /`schedule.py` /`reminder.py` ……，不如直接叫`Backend/modules/` 或`Backend/routes/` ，和`service/` 、`schemas/` 风格对齐。

### 3. middleware.py / exception.py 文件会膨胀（中）
把所有中间件塞进一个`middleware.py` 、所有异常塞进一个`exception.py` ，项目稍大后这两个文件会很长。建议改为 包 ：

`Backend/
├── middleware/
│   ├── __init__.py
│   ├── auth.py       # JWT 校验
│   ├── cors.py
│   ├── logger.py     # 请求日志
│   └── rate_limit.py
└── exceptions/
    ├── __init__.py
    ├── auth.py       # Token 过期/无效
    ├── schedule.py   # 课表冲突
    └── common.py     # 通用 4xx/5xx`

这样`main.py` /`app.py` 里 import 也更清晰。

### 4. docs/reminder.txt 定位尴尬（低）
`reminder.txt` 放在`docs/` 里，但内容是"开发过程中所遇到的问题、解决方法"——这更像 项目笔记/踩坑记录 ，和 API 文档、数据库文档性质不同。两个选择：

- 改名为`docs/NOTES.md` 或`docs/TROUBLESHOOTING.md` ，并升级为 Markdown；
- 或者移到项目根目录叫`DEV_NOTES.md` ，和 README 平级。
另外`plan.md` 本身已经是项目计划文档，`docs/plan.md` 和根目录`plan.md` 容易重复。建议根目录只留`README.md` +`plan.md` （开发计划），`docs/` 放技术文档（API、数据库、部署手册），职责分开。

`test/

### 注册漏洞发现与解决
在注册时不点击激活邮件，账号密码邮箱等依旧保留到数据库，但用户无法登录也无法注册，形成僵尸账号
补救解决方法：添加"未激活账号可被同邮箱重新注册覆盖"的自愈逻辑
注册查重只拦已激活账号：register_user 查到同邮箱记录时增加 is_active 判断——
已激活 → 仍返回"邮箱已注册，去登录"；未激活 → 不报错，走覆盖分支刷新 登录不直接判死：login 遇到 is_active=False 不拒绝到底，返回引导文案
链接失效无需找管理员，重新注册即补发新链接

遗留问题：用户 换了新邮箱 + 忘了原用户名 再注册 → 新邮箱查无记录，但`name_owner` 查重会发现用户名被那条未激活记录占着 → 依然被拦，且没有清理机制，用户名 永久锁死 。
 （ ）届时在任何一用户点击注册时将token超时的待激活账号删去以防止恶意占用选名池。

### 6. 缺一个"定时提醒"的归属（高）
你的项目核心卖点之一是"每节课前主动提醒"，但当前结构里：

- `scripts/schedule.py` 叫"任务调度脚本"——名字和`Backend/usr/schedule.py` （课表） 严重冲突 ，极易误 import；
- 真正的"主动提醒"逻辑（查课表 → 算通勤 → 发提醒）散落在哪并不明确。
建议：

`scripts/
├── migrate.py
├── seed.py
└── scheduler.py        # 重命名，APScheduler / Celery 入口

skill/
└── skill_remind.py     # 主动提醒的核心 skill：查课表 + 查天气/地图 + 推送`

`skill_remind.py` 由`scripts/scheduler.py` 定时触发，也允许用户通过自然语言由 orchestrator 调用。 "主动服务"的闭环就串起来了。


### 询问AI得知：
### "同时部署"只在开发期成立
- 开发模式 ：Vite(5173) + FastAPI(8000) 两个进程同时跑 ✅
- 生产模式 ：可以只跑 FastAPI 一个——用`npm run build` 打包出静态文件，再让 FastAPI 用`StaticFiles` 挂载，一个端口搞定，Vite 退役。plan.md 里`/frontend` 那节写的正是这个方案。

浏览器把请求交给 Vite，Vite 把`/auth` 开头的请求转发给后端；后端的 FastAPI 按路径命中 auth.py 里的函数，函数算出结果后把响应原路返回，经 Vite 带回浏览器。

标识符是契约，改名 = 双向协议变更 。动手前`Ctrl+Shift+F` 搜全项目，或者干脆立个约定： 跑通验收之前不改名 ，等链路全绿了再做一次性的"重构改名 + 全局替换"，风险小得多。
